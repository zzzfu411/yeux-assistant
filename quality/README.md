# 学习评阅固定案例

`learning-cases.json` 包含 GSE、数据库和软件工程各 5 个自行编写的合成案例：正确、错误、部分回答、套话和缺少资料。案例内容不代表课程官方要求，也没有使用个人课件。

运行离线检查：

```sh
pnpm exec vitest run tests/assessment.test.ts tests/evaluation.test.ts tests/quality.test.ts
```

离线检查检验证据守卫和上下文契约。部分夹具故意返回虚假的通过判定、伪造摘录或错版本引用。夹具已经指定了模型返回，因此 **15 项通过不代表模型教学准确率**。摘录在原文中存在，也不证明模型理解了它。

`retry` 只用于有依据的明确错误或矛盾；回答正确但缺少部分要素、仅作自述或缺少资料时用 `unclear`。纯自述等语义规则由模型评阅，代码不使用短语黑名单假装判断理解。`pass` 与 `retry` 都必须带有可核对的回答摘录、实际提供的资料版本和引用范围；缺少完整题目或依据时降为 `unclear`，保留已有复习阶段。模型自评与本人明确自评分别记录。`assessment_audit` 只保存结构有效且实际应用到回答的模型回复；无效 JSON 或不符合结构的回复会失败重试，不在此审计记录中。

真实模型验收应复用相同案例，但不采用 `proposed` 和 `fault` 夹具字段：仅发送 `material`、`question`、`answer`，使用应用相同的结构与提示词，再保存原始评阅、守卫结果及模型标识。由 `expected` 和 `rubric` 人工复核判定、反馈是否正确，以及引用是否支持结论。分别报告错误通过、错误拒绝、信息不足处理和引用错误；同时比较守卫前后的结果。

此步骤需明确触发后再读取本项目现有私有模型配置。只发送本目录的合成案例，不发送个人学习记录、资料或密钥到报告；不得把测试结果自动写入真实学习进度。真实调用与逐项结果在项目 SPEC 和本地私有报告中单独记录。

## 执行真实模型评测

先预演：

```sh
pnpm quality
```

默认只核对 15 个固定案例，不读取模型配置或密钥，不启动数据库，也不联网。明确执行后才调用：

```sh
pnpm quality --live --config /绝对路径/config.json
```

脚本只复制配置中的 `llm` 设置，不读取学习资料、邮件或生产数据库。Docker 需已运行，且本机已有 `postgres:18-bookworm` 镜像；脚本不会安装工具或自动下载镜像。外部 `DATABASE_URL`、`PGHOST` 等数据库环境变量会被拒绝。每项使用独立的合成会话与执行记录，顺序发送一次，最多 15 次请求，不自动重试；调用沿用应用的 5 次 / 180 秒运行预算，单请求最多 90 秒且不超过运行剩余时间；本工具每项只使用一次请求。模型预算回归需要独立 PostgreSQL：`pnpm verify` 包含 60 秒响应、90 秒超时、剩余时间、迟到响应和跨重试预算检查。

可以明确选择固定案例做修复诊断；重复 `--case` 选择多项，拼错或未知 ID 会在读取配置前失败。预演输出列出可用 ID：

```sh
pnpm quality --case gse-correct --case gse-partial
pnpm quality --live --config /绝对路径/config.json --case gse-correct --case gse-partial
```

子集报告标记 `selection: "subset"`，不能代替 15 项整体比较。评测逐项输出编号和状态；连续三次实际网络或 HTTP 失败后停止发出请求，后续项标为 `not_run`。人工停止后的未调用项标为 `cancelled`；正在等待的请求结束或超时后完成清理。两者都不会计入网络错误，也不会被算作通过。

发给模型的案例内容只有材料、题目和回答，来源编号使用不含答案标签的中性编号。`expected`、`rubric`、`proposed`、`fault`、课程分类与案例名称均不发送。模型共享资料开关沿用配置；若关闭，报告会明确记录，证据不足不会计作通过。

结果保存在本项目忽略的 `private/quality-*/report.json`，包含原始评阅、证据守卫结果、预期判定与人工核对标准、模型名、调用数、已记录用量、延时及逐项错误。API key 和完整模型地址会被替换；无用量记录表示未知，不表示免费或未消耗。原始判定与守卫结果分别计算一致率，分母始终为本次选择的全部案例，包含错误、未运行和取消项；默认选择全部 15 项。`errors` 记录执行错误，`networkErrors` 仅统计实际发出的网络或 HTTP 失败，`notRun` 和 `cancelled` 单列。`guardDowngrades`、`invalidCitationCases`、`engineeringErrors` 用于区分证据协议失败与语义判定差异。

评测结束后移除临时 PostgreSQL 容器及复制的模型配置，`cleanup.json` 记录结果；清理失败返回失败状态并指出需要核对的容器。报告保留，生产学习记录保持不变。退出码 `0` 只表示评测及清理完成，`2` 表示存在错误、未运行或取消项（报告为 `completed_with_errors`），`1` 表示启动或清理失败；任何退出码都不代表教学质量已通过人工验收。

## 案例修订与结果保留

2026-10-03 的首轮完整真实评测为 12/15 自动一致、1 项超时；独立 Agent 复核发现一次自然语言表达被过度要求格式，以及 `se-partial` 原句“把需求列出来就行。”与 unclear 标签有歧义。现将该回答澄清为“我先把需求列出来。”，仍要求补充测试、结果及用途。通用评阅允许同义表述和操作已建立的场景条件，避免要求重复固定小标题。原始报告、原案例与提示词单独留存，不重算旧分数；两项修订诊断均返回预设判定，并核对了反馈与原文引用；这不代表新案例集或新提示词已完成全量验收。

## 检索基准

`retrieval-cases.json` 是 30 份自行编写的合成资料（数据库、软件工程、本课程、个人资料与办事记录、通知）和 22 条查询，每条查询标注一份最相关的资料。测试另按固定种子生成 400 份由常见课程词汇拼成的干扰笔记，模拟大量共享常用词的课程资料；它们永远不是正确答案。

```sh
RUNTIME_TEST_DATABASE_URL=postgres://…/assistant_runtime_test pnpm retrieval:eval
RETRIEVAL_NOISE=3000 RUNTIME_TEST_DATABASE_URL=… pnpm retrieval:eval   # 一次性的延迟测量
```

测试在同一语料上运行旧实现（两字词 `ILIKE`、只取最后 48 个词、按命中词数排序，保留在测试文件里作对照）与当前实现（索引列 `app.chunks.lexemes` + BM25），输出 recall@5、MRR 与平均耗时，并要求当前实现不低于旧实现、recall@5 不低于 0.9。它还逐份核对 TypeScript 与 SQL 两边的切词结果一致。数据库必须是以 `_runtime_test` 结尾的专用测试库。

这只衡量“相关资料是否排在前面”，不衡量模型据此写出的答案是否正确。旧实现在并列分数时按随机 ID 排序，MRR 会在几次运行间小幅波动。

## 办理通知测量

`errand-cases.json` 是一份合成的学术报告会报名通知、一份合成的本人信息（故意缺学号）和一段合成回答。脚本用临时 PostgreSQL 和真实执行器走完“抽取要素 → 计划（追问）→ 回答 → 计划 → 写信”，从运行记录读出每一步的首字节时间、耗时与 token，并对要素和邮件主题做字面核对。

```sh
pnpm errand:eval                                   # 预演：不读密钥、不联网
pnpm errand:eval --live --config private/config.json --case seminar --max-calls 6
```

需要已手动启动的 Docker；`--max-calls` 为 1–10，是整个流程的上限。不发送邮件，不连接实际助手数据库；结果保存在 `private/errand-eval-*/`（`report.json` 与 `letter.md`）。信件是否得体仍需本人阅读。
